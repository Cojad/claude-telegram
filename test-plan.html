01 / 判斷原則

什麼值得寫測試

會咬人

今晚柯柯的 mention regex 從設定當天就沒生效過, 沒人發現, 因為沒有任何測試會去跑那條 regex. 這種「壞了但沒人知道」的邏輯優先.

是安全邊界

gate() 決定誰的訊息能送進 Claude, 判斷錯的代價是未授權的人講話被聽進去, 或該聽的人被擋掉, 兩個方向都要測.

會靜默腐化

純文字輸出 (chunk 分段) 沒有回饋迴路, 壞了不會有人告訴你, 只會有一則訊息內容悄悄跑掉幾個字.

不夠格上榜

純粹重複宣告 Telegram API 型別, 或只是把 grammY 的 ctx 包一層轉呼叫的地方, 測了只是在測 grammY 本身.

02 / 結構性前提

這三個函式現在測不了

gate() / isMentioned() / chunk() 都沒有被 export, server.ts 本身是一支有 top-level 副作用的 script, 一 import 就會建立 bot 並嘗試搶 poller. 現有的 poller-lifecycle.test.ts 是用 spawn 整個 process 繞過這點, 一條測試要等 process 真的啟動, 跑完兩條要 7 秒. gate/isMentioned 的分支數量比 poller 多得多, 照同樣的方式測, 一輪要跑十幾秒到幾十秒, 而且每個分支都要真的建立一個假的 Telegram Update 物件去戳 process 的 stdin, 又貴又間接.

前置工作: 這四組測試裡, 前兩組 (mention / gate) 需要先把這幾個純函式抽出獨立檔案 (不用等整個六模組拆完, 只要 policy.ts 這一小塊), 抽出來之後單元測試是毫秒等級, 不用 spawn process. 這剛好是模組化 plan 第一階段的一部分, 建議測試優先於重構本身動手, 先靠測試把現有行為釘住, 再拆檔案, 比先拆完才補測試安全.
03 / 建議的四組測試

mentionPatterns 是否真的觸發點名

isMentioned() · 需先抽成純函式
P0 · 今晚的真事故

為什麼: 直接對應今晚發現的事故, ^柯柯\b 這種 pattern 在 Bun 的 JS regex 引擎裡因為 \b 不認 CJK 字元, 從設定當天起就沒生效過. 這組測試的唯一目的是: 給一段文字跟一組 pattern, 判斷結果符不符合預期, 用真正的 runtime (bun test 本身就是 bun) 執行, 不會再犯拿別的語言代測的錯.

輸入文字pattern預期理由
柯柯 早安^柯柯觸發開頭點名, 今晚修過的正確版
柯柯 早安^柯柯\b不觸發舊版壞掉的樣子, 這條測試存在的意義
嗨嗨 柯柯^柯柯不觸發點名詞不在開頭, 設計如此
cc 早安^cc\b觸發ASCII 邊界正常運作
ccxxx 早安^cc\b不觸發\b 對 ASCII 有效, 防止誤觸發
(任意文字)— reply_to_message.from = bot觸發回覆機器人視同點名, 與 regex 無關的另一條路徑

gate() 的放行 / 丟棄矩陣

gate() · 需先抽成純函式
P0 · 安全邊界

為什麼: 這是唯一決定「誰的話會被送進 Claude Code」的邏輯. 測試目的不是窮舉每個欄位組合, 是釘住幾個真正有後果的邊界: 不在名單的人講話會不會被放行 (太寬鬆 = 安全問題), 該放行的會不會被誤擋 (太嚴格 = 功能壞掉, 今晚也真的發生過).

情境預期 action
私訊, sender 在 allowFromdeliver
私訊, sender 不在 allowFrom, dmPolicy=allowlistdrop
私訊, sender 不在名單, dmPolicy=pairing, 無 pendingpair (新配對碼)
私訊, 已有 pending 配對, 第 3 次詢問drop (超過 2 次提醒上限)
群組, groupId 不在 access.groupsdrop
群組, groupAllowFrom 非空且 sender 不在其中drop, 不管有沒有點名
群組, requireMention=true, 訊息有點名deliver
群組, requireMention=true, 訊息沒點名drop

chunk() 不能切斷字元, 不能超過上限

chunk() · 現有函式已可直接測
P1 · 靜默腐化

為什麼: 兩個具體風險, 都讀原始碼就看得出來, 不是假設性的. 一是 rest.slice(0, cut) 用的是 UTF-16 code unit 索引, 如果切點剛好落在一個 surrogate pair 中間 (常見於某些 emoji), 會把一個字元切成兩半, 兩邊都變成不合法字元. 二是純長度模式沒有任何上限保護, 若呼叫端傳一個超大 limit, 沒有防呆.

情境預期
文字長度剛好等於 limit回傳單一區塊, 不觸發分段
文字比 limit 長 1, mode=length分成兩塊, 每塊都 ≤ limit
mode=newline, 切點前有段落換行優先在段落邊界切, 不是硬切在 limit
硬切點剛好落在 emoji (surrogate pair) 中間切點前移, 兩塊都不含孤立的半個字元
所有分段接回去與原文字完全相等 (無遺失無重複)

pruneExpired() 的 pairing 逾期

pruneExpired() · 需先抽成純函式
P2 · 低風險, 順手補

為什麼: 邏輯單純 (單一 TTL 比對), 出錯後果也小 (頂多配對碼晚一點失效), 一條測試釘住「過期會被清掉, 沒過期不會」就夠, 不必展開.

04 / 明確不做

bot.on 的各種訊息 handler (text/photo/document/…) 與 MCP CallToolRequestSchema 暫不寫測試. 這些主要是把 grammY 的 ctx 轉呼叫 handleInbound / Telegram API, 要嘛需要真的打 Telegram 的網路請求, 要嘛要建一整套假的 grammY Context 物件, 兩種成本都高, 而且測到的多半是 grammY 或 Telegram API 本身的行為, 不是這支程式自己的邏輯. 等模組化把 handleInbound 拆成純粹的協調邏輯 (輸入一個已解析的 InboundUpdate, 呼叫 policy, 呼叫 sink) 之後, 這塊會自然變得好測, 現在硬測不划算.
