03 / 延伸方向

讓 inbound 不必只認得 Claude Code

TODO · 尚未排進施工順序

現在 inbound 判斷完一則訊息該不該送之後, 只有一條路可以走: 呼叫 mcp.notification 送一個 claude/channel 通知, 這條路綁死在跟 Claude Code 之間那條 MCP stdio 連線上. 收到之後要不要理, 理了要怎麼呈現, 完全是對方自己的規矩, 這支程式管不到也看不到, 它只負責喊話. 這不是這支程式天生綁死 Claude Code, 只是「喊話要對著哪個頻道」目前寫死成一種.

構想: 把送出去那一步換成介面
interface InboundSink {
  emit(event: InboundEvent): void | Promise<void>
}
// handleInbound 判斷邏輯完全不變, 只是最後一步
// 從寫死呼叫 mcp.notification, 換成呼叫 sink.emit(event)
現行

McpChannelSink

就是現在這條路, 送 notifications/claude/channel, 只有 Claude Code 這種真的用 MCP protocol 對話的 client 聽得到.

構想

HttpWebhookSink

POST 到指定的網址, 任何能收 HTTP 的東西都能接, 不限定是不是 agent harness.

構想

StdioLineSink

本機吐一行 JSON 給同機的小程式讀, 比 HTTP 更省, 最適合輕量自製 harness+LLM 這種單機小迴圈.

構想

QueueSink

丟進 Redis / SQS 之類, 給非同步, 多消費者的場景, 優先度最低.

outbound 那四個 MCP 工具也是同樣的問題換個角度: 現在包成 MCP tool 是因為 Claude Code 這種 agent 靠工具呼叫運作, 但輕量自製 harness 不需要這層協議開銷, 直接呼叫函式送訊息就好. 真正要拆的是「跟 Telegram 對話的核心邏輯」跟「暴露給呼叫者的介面」這兩層, policy / inbound / poller / store 這些核心邏輯完全可以原封不動被其他 harness 重用.

04 / 小改動

meta 補上被回覆訊息的 id

Telegram 的原始更新其實會直接內附 reply_to_message 整個物件 (最近的訊息都有, 太舊的可能被省略), handleInbound 目前只用它的 username 判斷完就丟掉. 先把這個順手撿起來.

現在, server.ts:940
meta: {
  chat_id,
  message_id: String(msgId),
  user: from.username ?? String(from.id),
  user_id: String(from.id),
  ts: ...,
}
改動後
meta: {
  chat_id,
  message_id: String(msgId),
  user: from.username ?? String(from.id),
  user_id: String(from.id),
  ts: ...,
  ...(replyTo ? {
    reply_to_message_id: String(replyTo.message_id),
    reply_to_text: truncate(
      replyTo.text ?? replyTo.caption, 200),
  } : {}),
}
已知限制: Telegram 不保證太舊的訊息會內附完整 reply_to_message, 遇到只有 id 沒有文字的情況, 就要靠下一節的 store 回頭查, 這也是為什麼這兩項要一起做.
05 / 主要功能

用 SQLite 記住每一則訊息

bun 內建 bun:sqlite, 不用加依賴. 寫入時機定在 inbound 判斷之前 (不論放不放行都記), 跟 outbound 送出之後, 兩邊都寫進同一張表, 用 (chat_id, message_id) 建索引, 對應你要的「必要時回頭查閱理解上下文」。

欄位型別說明
idINTEGER PK自增流水號
chat_idTEXT與 index 一起用
message_idTEXTTelegram 原生 id, 與 chat_id 合成唯一索引
directionTEXTin / out
user_idTEXT發送者 (out 則是 bot 自己)
tsTEXTISO8601 UTC
contentTEXT文字本體
reply_to_message_idTEXT NULL沿用上一節的欄位
attachment_kind / file_idTEXT NULL沿用現有 AttachmentMeta
deliveredINTEGER0/1, 是否通過 gate() 送進 Claude

配一個新的 MCP 工具 lookup_message: 帶 chat_id + message_id 查單筆 (拿來補 reply_to_text 沒帶到的情況), 或帶 chat_id + limit 查最近幾筆當作補充脈絡, index 走 UNIQUE(chat_id, message_id), 查詢都是 O(1) 等級.

順便解掉今晚的另一個缺口: delivered=0 的那些也存, 之後查「這則訊息到底有沒有被丟棄, 為什麼」不用再靠猜的.
